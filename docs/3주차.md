4. 네 프로젝트에 적용하기
   4-1. 글 수정(PUT): 낙관적 락 적용 (핵심)

게시글 수정은 충돌이 드물고, 충돌하면 사용자에게 알려주는 게 자연스러워서 낙관적 락이 맞아.

Post에 @Version 필드를 추가해.
충돌 시 ObjectOptimisticLockingFailureException이 터지니, GlobalExceptionHandler에서 잡아서 409 Conflict로 변환해. 에러 코드(예: POST-011, "다른 사용자가 먼저 수정했습니다. 새로고침 후 다시 시도해 주세요")를 PostErrorCode에 추가해.
중요한 함정: 서버 안에서 "읽고 → 수정하고 → 저장"하는 시간은 몇 밀리초라서 충돌이 거의 없어. 진짜 갱신 손실은 사용자가 수정 화면을 열어 두고 한참 뒤에 저장할 때 생겨. 이걸 막으려면 조회 응답에 version을 담아 주고, 수정 요청이 그 version을 다시 보내게 해서 서버가 비교해야 해. 이 부분을 넣을지는 네가 정할 설계야(Swagger 문서와 요청 DTO에도 영향을 줘).
4-2. 조회수: 락이 아니라 원자적 UPDATE 쿼리

조회수 증가에 낙관적 락을 쓰면 안 돼. 이유는 두 가지야.

조회할 때마다 버전이 올라가서, 동시 조회끼리 충돌이 계속 나.
더 큰 문제는, 누가 글을 보는 순간 버전이 바뀌면 글을 수정하던 사용자의 저장이 실패해. 조회가 수정을 방해하는 거지.

그래서 조회수는 UPDATE post SET view_count = view_count + 1 WHERE id = ?처럼 한 번의 쿼리로 처리해(버전은 건드리지 않게). 이러면 락 없이도 정확해. 앞에서 말한 "삭제와 조회수 증가가 겹쳐도 글이 부활하지 않는" 효과도 같이 얻어.

4-3. 수정과 삭제가 겹칠 때

수정하는 사이 글이 삭제되면 WHERE id = 5 AND version = 3에 맞는 행이 없어서 같은 낙관적 락 예외가 나. 이 예외를 409로 응답할지, "글이 없다"는 404로 구분할지는 에러 응답 정책에 따라 정해.

4-4. 좋아요: 락이 필요 없다

좋아요 중복은 유니크 제약이 마지막 방어선이야. 락 없이 (member_id, post_id) 유니크 제약 위반 예외를 ALREADY_LIKED로 바꾸면 돼. 좋아요 수는 count 쿼리로 구해.

4-5. 비관적 락은 어디에 쓸까

솔직히 지금 게시판에는 비관적 락이 꼭 필요한 곳이 거의 없어. 정확성이 최우선이면서 같은 행에 동시 쓰기가 몰리는 경우(재고, 포인트, 한정 수량 이벤트)에 쓰는 도구라서, 이 과제 범위에서는 개념과 차이를 이해하는 것이 목적이야. 굳이 체험해 보고 싶다면 실험용으로 이런 걸 해볼 수 있어.

임시 엔드포인트를 만들고 @Lock(PESSIMISTIC_WRITE) 조회 후 일부러 몇 초 대기를 넣는다.
그 사이 다른 요청이 같은 행을 수정하려 할 때 기다리는 걸 로그와 응답 시간으로 확인한다.
확인 후 임시 코드는 지운다.
5. 헥사고날 구조와 부딪히는 점

@Version 필드는 JPA 엔티티에 있어야 해.

A 방식(도메인 Post에 어노테이션): Post에 필드만 추가하면 돼서 간단해.
B 방식(엔티티 분리): 버전 값이 도메인 Post와 JPA 엔티티 사이를 오가야 해. 도메인에 version 필드를 들고 있다가 저장할 때 어댑터가 그 값을 엔티티에 실어야 낙관적 락이 동작해. 이걸 빠뜨리면 락이 조용히 무력화돼.
