# 인증 흐름 정리

## 왜 Access Token과 Refresh Token을 나눌까?

Access Token은 API 요청에 `Authorization: Bearer ~`로 넣고 10분 뒤 만료
-> 노출되어도 피해 시간이 짧음

Refresh Token은 14일 동안만 유효하고 JavaScript가 읽지 못하는 HttpOnly 쿠키에만 둔다
Access Token이 만료되면 쿠키를 보내고, 서버는 새 Access Token과 새 Refresh Token을 함께 발급

```text
로그인 → Access Token(응답 헤더) + Refresh Token(HttpOnly 쿠키)
API 요청 → Authorization: Bearer Access Token
만료됨 → POST /auth/refresh + X-XSRF-TOKEN
        → 기존 Refresh Token 소비 → 새 토큰 2개 발급
```

Refresh Token의 원문은 데이터베이스에 저장하지 않고 SHA-256 해시만 저장
같은 Refresh Token이 두 번 제출되면 세션을 폐기
-> 새로고침 등으로 동시에 재발급 요청이 와도 한 요청만 성공

## 기존 게시글 요청은 어떻게 흐를까?

```text
PostController
  → PostUseCase
    → PostService
      → PostRepository (포트)
        → PostRepositoryAdapter
          → PostJpaRepository
```

Controller는 HTTP와 JWT에서 사용자 ID를 꺼내는 일만 함
Service는 작성자 확인, 탈퇴 회원 검증처럼 업무 규칙을 실행함 
Repository 포트는 Service가 JPA 구현에 직접 묶이지 않게 함

## 제목 검색 조건은 어디에 두나?

PostController는 `title` 쿼리 파라미터를 받고 GetPostsCommand로 전달
Command는 페이지 번호처럼 유스케이스 입력을 검증
-> 실제 LIKE 조건과 %, _ 이스케이프는 DB 문법이므로 PostSpecifications에 두도록 선택함. 
-> 웹 규칙, 유스케이스 규칙, DB 규칙을 섞지 않기 위해.!

## EntityGraph와 DTO Projection

현재 목록 조회는 게시글과 작성자를 함께 가져온 뒤 Response로 바꾼다. 
작성자 이름이 필요한 구조에서 N+1을 피하기 쉽고 도메인 객체도 재사용할 수 있다.

목록에 통계/조인/표시용 컬럼이 크게 늘어나면 DTO projection을 별도 조회 어댑터에 두는 편이 효율적이라고 판단했다
조회 SQL과 응답 DTO가 더 강하게 연결되긴 하겠지,,

## Kakao Adapter가 필요한 이유?
Kakao의 id, properties.nickname은 외부 서비스의 표현
OAuth2LoginSuccessHandler는 그 값을 provider=KAKAO, providerSubject, nickname으로 변환해 
AuthService에 전달
내부 로그인 로직은 Kakao JSON 구조를 알 필요가 없고~
다른 제공자를 추가할 때는 같은 내부 입력을 만드는 Adapter만 더하면 될듯

# 헥사고날 구조 더 파보기
- Controller는 HTTP 요청, JWT 주체 추출, 응답 헤더·쿠키 설정만 담당
- AuthService, PostService는 로그인, 토큰 회전, 작성자 검증 같은 유스케이스와 트랜잭션을 담당
- 서비스는 MemberRepository, PostRepository 같은 포트에 의존
- JPA 접근은 MemberRepositoryAdapter, PostRepositoryAdapter 같은 바깥쪽 Adapter가 담당
- JWT 발급 정책은 TokenService에 모음 -> AuthService는 JWT 문자열을 직접 만들거나 파싱하지 않음
- Kakao 응답 구조는 OAuth2LoginSuccessHandler에서 내부 입력값으로 변환.. 
- 나중에 다른 것들 추가해도 서비스 계층이 외부 응답 JSON 구조를 모르도록..

## 추가 공부
1) Refresh Token에 대해
지금은 DB 세션 + Refresh TOken 회전 방식으로 구현했다. 재사용을 감지할 수도 있고, 서버를 재시작한 뒤에도 유지되며, 바로바로 무효화가 되기 떄문이다.
근데 보호 API마다 세션 DB를 조회해야 한다는 트레이드오프가 있다.

-> Access Token 블랙리스트도 비슷한 트레이드오프가 있다

2) Caffeiene 로컬 캐시에 대해
구현은 비교적으로 단순하지만, 서버를 재시작하거나 서버가 많은 환경에서 무효화 상태가 사라지게 된다.. 그래서 지금 이 과저에서는 caffeine도 좋은 선택지라 생각한다

-> Redis로 저장하는 방법도 있겠지만,, 그거까지는 너무 오버엔지니어링 + 어차피 앱잼때 하게 되어있기 때문에 DB세션 + Refresh Token 회전하는 식으로 구현했다

3) 회원가입/로그인/회원탈퇴 등
BCrypt 해시 사용해서 회원가입한 정보들 저장하고, 이메일도 정규화하고, 중복확인하는 로직도 포함시켰다.
BCyrptPasswordEncoder 통해서 비밀번호를 암호화하는 것도 추가해봤다

4) 인증, 인가
filterchain이 접근 정책을 정하는 방식으로 구현했다 (필수 과제)
- 게시글 생성의 경우에는 JWT의 sub 사용하도록 했고 (memberId말고)
- 수정/삭제는 verifyOwner가 토큰의 회원 ID랑 게시글 작성자 ID랑 동일한지를 확인한다

-> Controller에 role (어드민) 붙이는 방식이나, service에 직접 권한 검사를 넣는 방식 등.. 이 있을 것 같다 (다른 구현 방법에 대해 생각을 해보자면)
일단 나는 큰 접근 정책은 filterchain에 넣어놨고, 게시글 소유권은 postservice에 넣어놨다.
(서로 다른 규칙이라고 생각해서 분리함)

5) JWT 발급/검증/파싱,,,
AuthService가 jwt 문자열에 대해 접근하는 것도 권한을 Jwt 인코더, 디코더, TOkenService로 나눠놨다
그리고 서명 알고리즘은 'HS256 HMAC '방식을 선택해봤다. (리팩토링의 느낌으로..)

JWT에 대해 깊게 파보는 거는 처음이긴 해서.. 잘 모르지만..?
단일 서버이고 작은 서비스여서 HS256을 선택했고, RSA, ES256 같은 구현방법들도 있다. 얘네는 여러 API 서버가 공개키만으로 검증해야 할 때 유용하다고 한다

그리고 외부 인증 서버를 두는 방식도 있겠지만? 그거는 너무 투머치,,

나는 Resource server 방식으로 구현했는데, JWTㅇ 니증 필터를 직접 작성하는 대신에 spring security가 bearer 헤더 처리랑 인증 컨텍스트 설정을 맡도록 하는 방식이다.

아 그리고 OncePerRequestFilter 방식도 있다고 한다... (너무 어렵다)

6) 로그아웃/탈퇴 토큰 무효화
